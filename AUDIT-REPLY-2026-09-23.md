## Q1. Turn outcome policy

**Выбираю strict rollback; partial commit сейчас не вводил бы.** Для этого проекта частичный успех двух действий труднее объяснить пользователю, чем просьбу повторить turn. Приоритет — не оставлять инвентарь в состоянии, о котором финальный ответ говорит неверно.

Правило стоит сформулировать как проверяемый автомат, а не как «unresolved error»:

1. До первой успешной изменившей данные операции ошибки чтения можно исправлять в следующих раундах.
2. Ошибка mutation tool — немедленный rollback и failed turn. Ошибка любого tool после первой изменившей данные операции — то же самое.
3. Пустой финальный ответ после изменения — rollback.
4. Успешный no-op имеет `changed=false`; он не превращается в фиктивную мутацию.
5. После rollback можно сохранить reservation, текст пользователя и failed run log, но **не committed receipts**. Существующие предварительно сохранённые user messages не должны затем попадать в контекст как успешно выполненный turn: [сейчас они commit-ятся до запуска модели](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/runner.py#L62-L85).

Последний пункт — скрытая часть «rollback всего turn»: rollback бизнес-данных не откатывает уже сохранённый разговор. Нужно либо исключать failed turn из будущего контекста, либо явно представлять его как неисполненную попытку. Иначе следующее «попробуй ещё раз» модель увидит после предыдущего пользовательского запроса без понятного исхода.

## Q2. Write-target resolution

**Score никогда не должен давать право записи.** Resolver должен заново проверять сильное свидетельство в БД, независимо от `SearchInput.limit` и обрезанного списка кандидатов. Практичное начальное правило:

- Item: уникальное точное canonical name/alias с проверкой конфликтов **между** именами и alias; либо специально назначенный уникальный identifier. Совпадение обычного атрибута, tag, substring или FTS остаётся только read candidate.
- Location/Category: полный точный путь либо глобально однозначное точное имя листа; наличие дубля в другом родителе блокирует запись по короткому имени.
- Созданный в текущем turn объект может использоваться дальше после следующего раунда при сохранении текущего правила frozen capabilities.
- Неоднозначный объект требует уточнения. «Пользователь выбрал второй» нельзя считать доказанным только потому, что модель так интерпретировала текст; для действительно рискованной записи нужен выбор из показанного набора или отдельное подтверждение конкретного объекта.

Сохраняйте связь разрешения с исходным запросом и наблюдаемой версией объекта. Текущий `resolved` — накапливаемый набор ID на весь run; поздний поиск или ручное изменение записи между поиском и мутацией не отзывают раннее право. Минимум — повторно проверить имя/путь и уникальность непосредственно перед записью. Отдельный публичный capability-token пока не обязателен.

## Q3. Mutation receipts

Я бы использовал **`AgentRunResult` + отдельное поле в `AgentRunLog`**, а Event оставил бы доменной историей. Структура receipt: `operation`, `entity_type`, `entity_id`, `changed`, стабильные before/after ID там, где они нужны, и `event_ids`. Не копируйте в него описания, весь payload Event или исходный текст пользователя.

Receipt создаётся backend после успешного service flush как **предварительный** результат. Он становится committed receipt только вместе с финальным commit; при rollback список в successful result пуст. В failed trace можно оставить диагностику попыток, но явно пометить результаты как rolled back: ID события, полученный до rollback, не должен выглядеть подтверждением записи.

Поле в `AgentRunLog` даёт устойчивый ответ при повторе idempotency key без разбора произвольной структуры `tool_trace`. Event payload не следует превращать во вторую копию receipt: Category/Location операции могут вообще не порождать Item Event, а Event и receipt отвечают на разные вопросы. Это небольшое намеренное дублирование ссылок на Event ID, а не новая event-sourcing модель.

## Q4. Historical Location representation

Предпочитаю **snapshot компонентов пути для новых Events**, сохраняя стабильный leaf Location ID. Например, массив пар `{location_id, name}` для from/to на момент события в версионированном поле `Event.payload`. Это точнее готовой строки: имя может содержать `/`, а компоненты можно отображать и сравнивать без зависимости от разделителя. При move snapshot исходного и конечного пути нужно собрать до изменения ссылки Item.

Это использует существующий JSON payload и не требует менять frozen portable-v1: импорт уже переносит Event payload. Нужен тест export → import → render для нового поля. Старые Events без snapshot показывают ID и **явно маркированный текущий путь**; backfill нынешним путём был бы ложной историей. Rename/reparent дерева всё ещё не будет отдельным историческим событием — snapshot решает правдивость отображения Item Events, а не создаёт полный журнал изменений Location. Тот же вопрос возникнет для Category в `item_updated`, если Activity начнёт показывать исторические названия категорий.

## Недостающие adversarial tests

Наиболее ценные сверх вашего списка:

- `limit=1` при двух точных Item/alias совпадениях; alias одного Item совпадает с canonical name другого.
- Единственное точное значение **неидентифицирующего** атрибута и единственное слабое FTS-совпадение: оба доступны для чтения, оба не дают write permission.
- Mutation tool оставил dirty ORM state и вернул `ok=false`; следующий tool не должен случайно его flush-нуть.
- Успешная мутация → ошибка read tool → rollback; успешная мутация → поздний «исправленный» вызов → всё равно rollback по простому MVP-правилу.
- No-op move/update: `changed=false`, нового Event и подтверждения «перемещено» нет.
- Сбой непосредственно до commit, после commit до HTTP response и неопределённый результат самого commit; повтор с тем же ключом не выполняет вторую мутацию.
- Старый Event без snapshot, rename/reparent предка, одинаковые leaf names и новый snapshot после portable round-trip.
- Ручное изменение Item между поиском модели и записью; длинный сетевой раунд после первого flush при втором соединении SQLite.

## Скорректированный порядок

Ваши приоритеты верны, но **Stage A слишком широк**: он одновременно меняет write resolver, транзакционную политику, формат результата и подтверждение пользователю. Я бы разбил его, сохранив четыре-пять небольших implementation PR:

1. **Write target safety:** R1, R2 и adversarial проверки `limit=1`, alias collisions и provider schemas.
2. **Atomic turn outcome и receipts:** R3, R5; один commit boundary, failed-turn context и авторитетный результат API.
3. **Idempotency crash consistency:** R4 на подготовленной границе транзакции; fault injection и concurrent-key tests.
4. **Location truth в ручном интерфейсе:** сначала R7, затем unknown filter/suggestions R9; R6 оформить отдельным решением, если сценарии одинаковых экземпляров подтверждены.
5. **Historical evidence и Activity:** snapshot для новых Events, честная маркировка старых, затем переработанная read-only Activity assignment.

Архивирование 0012 — процессный шаг **до** первого stage, не дополнительный implementation stage.
