# Архитектурный, продуктовый и инженерный аудит

Снимок: main, commit [30c391a](https://github.com/buzlet/ah-there-it-is/commit/30c391ac44c0c32d5b4c62c62914740cc1e06ae5), 23 сентября 2026. Анализ выполнен через GitHub Connector. Код локально не запускался; воспроизведение новых сценариев и измерения задержек не заявляются. Последний implementation head Stage 22 имел успешные [application-ci](https://github.com/buzlet/ah-there-it-is/actions/runs/35894074744) и [provider-contract](https://github.com/buzlet/ah-there-it-is/actions/runs/35894074599). Обозначения: **Ф** — факт из кода/документов; **Р** — обоснованный риск; **Э** — гипотеза для эксперимента.

## Executive summary

Базовая архитектура соответствует личному local-first инвентарю: SQLite, стабильные ID, сервисные мутации, deterministic search и отдельная проверка LLM-провайдеров. Переписывать стек не нужно. Главная проблема теперь в семантике пользовательского действия, а не в выборе БД: tool API может принять неполную команду как снятие предмета с места; слабое поисковое совпадение может авторизовать изменение; agent способен зафиксировать часть действий после tool-error или выдать финальный ответ, не согласованный с фактически выполненными действиями. Между business commit и фиксацией статуса idempotency key есть окно неопределённости. Следующий полезный этап — усилить эти контракты и ручной путь для неизвестного места/одинаковых экземпляров, прежде чем добавлять новые каналы ввода.

## Десять главных проблем и рисков

**R1 · Неявное снятие с хранения — Critical, Ф.** [MoveItemInput](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/schemas.py#L74-L77) задаёт location_id с default=None; [handler](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/tools.py#L388-L396) передаёт его в move_item. Модель, забывшая аргумент, создаст item_taken и обнулит известное место. Исправить сейчас: сделать ключ обязательным, но допускающим явный null; отдельно проверить вызов с отсутствующим ключом и без мутации. Польза высокая, риск изменения низкий, S.

**R2 · Слабый поиск становится правом записи — Critical, Ф/Р.** [Одиночный кандидат всегда resolved](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/tools.py#L444-L465), даже если это FTS/substring; score gap 50 также даёт право. При запросе «переходник» единственный частичный результат может быть не тем экземпляром, но модель получит move/update. Исправить сейчас: отдельно классифицировать read candidate и mutation target; слабые совпадения требуют точного уточнения либо явного выбора пользователя, а не арифметического score. Не запрещать чтение слабых кандидатов. Проверить на случайном длинном описании и массовых похожих названиях. M.

**R3 · Tool-error не отменяет уже сделанное — Critical, Ф/Р.** Dispatcher превращает многие ошибки в обычный ответ ok=false, а [AgentRunner фиксирует всю транзакцию при любом финальном ответе без tool calls](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/runner.py#L85-L135). Сценарий: первый tool переместил A, второй ошибся на B, модель ответила «не получилось»; A уже записан. Исправить сейчас: явная turn outcome policy — при неразрешённой ошибке после мутации rollback или подтверждённый частичный результат с перечислением committed receipts. Детерминированный тест этого порядка обязателен. M.

**R4 · Окно между business commit и idempotency status — Critical, Ф/Р.** [Runner commit](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/runner.py#L118-L135) предшествует отдельному [mark_completed commit](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/services/chat_requests.py#L193-L256). Крах между ними оставляет processing без ссылки на уже выполненный run; повтор блокируется, а ручной recovery новым ключом рискует повторить действие. Исправить сейчас: в той же business transaction записывать request_key → run_id/status; reservation может остаться отдельной до вызова модели. Добавить fault-injection тест между commit и HTTP response. M.

**R5 · Ответ модели не доказывает выполненное действие — Critical/Next, Ф/Р.** [Финальный текст](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/runner.py#L110-L135) может быть пустым либо «готово» без единого mutation tool; успешный run всё равно фиксируется. Для инвентаря это ложная память. Исправить скоро: сохранить backend mutation receipts в результате turn; для записи формировать подтверждение из них или как минимум запрещать success-claim без соответствующего receipt. Это не требует prompt tuning. M.

**R6 · Одинаковые физические экземпляры недоступны пользователю — Next, Ф.** [Service поддерживает allow_duplicate](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/services/inventory.py#L147-L170), но [web-схема](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/web/schemas.py#L82-L94) и [tool-схема](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/schemas.py#L50-L60) его не дают. [Assignment 0010](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/agent-tasks/assignments/0010-stage21-manual-web-admin.md) запрещал это сознательно. Два одинаковых прибора в разных местах нельзя отслеживать по отдельности. Добавить в браузер явное «создать отдельный экземпляр» с показом существующих совпадений; LLM-путь — после выбора пользователя. M.

**R7 · Null location объединяет разные состояния — Next, Ф/Р.** [Item.current_location_id](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/db/models.py#L86-L110) nullable, [move_item(null)](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/services/inventory.py#L286-L311) пишет item_taken. Пользовательское «место неизвестно», «взял с собой», «продал» и «выбросил» неразличимы по текущему месту; suggestion может предложить старый ящик как вероятное нынешнее место. Минимум: явный reason/status при снятии с хранения и подавление suggestions для выбывшего; отдельную полноценную lifecycle-модель вводить только после реальных случаев. M.

**R8 · Исторический путь меняется задним числом — Next, Ф/Р.** Event хранит location ID, но [история в браузере строит путь из текущего дерева](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/services/catalog.py#L239-L253). После reparent «раньше лежал на балконе» может показываться как «в кабинете» без фактического перемещения вещи. Не менять стабильные ID; добавить immutable path/name snapshot в новые события или честно помечать путь как current path. Исправлять скоро до активной реорганизации мест. S/M.

**R9 · Ручной fallback не показывает unknown и inferred как рабочий поток — Next, Ф.** [Item list](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/web/templates/items.html#L17-L32) показывает неизвестное место как «—»; [suggestions](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/services/location_suggestions.py#L50-L73) доступны agent tool, но нет соответствующего маршрута. Когда LLM отключена, пользователь не может отфильтровать потерянные вещи и увидеть evidence. Добавить фильтр «место неизвестно» и read-only suggestions в Item detail с явным отличием от known location. S/M.

**R10 · Полные traces не имеют ограниченного жизненного цикла — Next, Ф/Р.** [RunLog](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/db/models.py#L229-L257) хранит prompt, прошлые сообщения и tool results; [adapter info](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/openai_compatible.py#L71-L88) копирует произвольный extra_body. Личные описания и потенциальные секреты внутри extra_body остаются в active DB/backup и доступны через локальные eval-страницы. Сейчас ввести allowlist/редакцию config и явную политику хранения/очистки operational traces при сохранении domain events; удаление исторических данных — только отдельным продуманным действием. S/M.

## Пять вещей, которые оставить

- SQLite + синхронный SQLAlchemy: для нескольких тысяч строк нет доказанной причины менять storage или вводить async.
- Stable IDs для всех ссылок и запрет свободнотекстовой записи через LLM.
- FTS5 как восстановимый индекс и явный doctor/repair; embeddings пока не нужны.
- Строгое разделение full backup, frozen portable-v1 и empty-db bootstrap.
- Серверный Jinja/обычный JS и deterministic mocks в application CI.

## Пять кандидатов на упрощение или заморозку

1. **Документный статус.** AGENTS.md, HANDOFF.md, README и assignment/review повторяют stage-факты. Оставить краткие актуальные инварианты и ссылки на исторический архив; старые документы не переписывать.
2. **Experiment replay UI.** [Отдельные tables и сервис](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/services/experiments.py#L51-L96) полезны для исследований, но не для базового поиска вещей. Заморозить развитие до появления регулярного использования, не удалять пользовательские данные.
3. **HeuristicLLMClient.** Оставить как smoke fixture, не развивать в третий production NLP-стек рядом со scenario mock и real providers.
4. **Четыре параллельных чтения одного Item.** CatalogService, ToolDispatcher, SearchService и portable export имеют разные DTO; не вводить generic repository, но вынести общую семантику отображения known/current/unknown и ограничений истории только если расхождение уже подтверждено.
5. **Обязательные ритуалы stage.** Protocol v4 разумно сохраняет seed, но AGENTS/HANDOFF/README обновления и полный локальный набор проверок для каждого малого docs-only шага избыточны. Держать один seed, один PR и проверку изменённой области; полный набор для code/schema/runtime изменений.

## Отсутствующие пользовательские возможности

**Скоро:** отдельные одинаковые экземпляры; частичное движение количества (2 из 5) либо явный выбор «разбить запись»; unknown/in-use/disposed status; фильтры по месту/state/category и read-only suggestions в браузере; простое исправление/отмена последнего ошибочного действия; понятный backup reminder и проверка восстановления; импорт новых данных в уже непустой инвентарь хотя бы через preview + ручное сопоставление, если onboarding 1000 вещей станет реальной задачей.

**Позже:** быстрый bulk edit и CSV preview; отметка даты физической проверки места; мобильная эргономика/печать меток после изучения повседневного использования; вложения/фото только если названия и атрибуты не справляются.

**Вероятно не нужны сейчас:** cloud sync, multi-user ACL, SPA, vector database, общий event-sourcing, async ORM, универсальная plugin-платформа, voice/Telegram/QR до появления измеренного спроса.

## Подробный анализ по 17 областям

### 1. Архитектура
Ф: domain содержит нормализацию/state/DTO, InventoryService напрямую использует SQLAlchemy и владеет validation/commit; это приемлемо для данного масштаба. Web и tools тонкие на запись. Р: семантика «что означает unknown», «насколько кандидат надёжен» и «успешен ли turn» сейчас распределена между search, dispatcher, prompt и UI. Нужна не новая repository-абстракция, а небольшие общие typed outcomes для resolution и mutation receipt. См. R2, R5, R7.

### 2. Независимость от LLM
Ф: [LLMClient](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/protocol.py#L14-L72) узкий; ScenarioLLMClient гоняет реальный backend без сети; CI отделён. Ограничение: mock заранее задаёт аргументы tools, а [пять model probes](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/eval/model-probes-v1.json) проверяют общий протокол, не динамическую схему и не корректность выбора ID в реальном приложении. Это правильное разделение тестов, но не свидетельство, что любая модель успешно пользуется приложением. Код должен закрыть R1–R5; model pipeline затем измеряет usability, а не безопасность.

### 3. Domain model
Ф: Item имеет quantity≥1, nullable location, state, JSON attributes; Category/Location — отдельные деревья; container-as-item явно не связан с Location. Quantity означает группу, которую нельзя переместить частично; одинаковые физические вещи доступны лишь через service override. Состояния new/used/working/broken/for_sale/discarded смешивают физическое состояние с жизненным циклом; допустимо сейчас, но создаёт неоднозначность. Минимальная продуктовая проверка — 20 реальных записей с одинаковыми предметами, расходниками и контейнерами; до неё не строить универсальную ontology.

### 4. Identity и история
Ф: normalized_name использует NFKC/casefold/whitespace, ID не меняется при rename/reparent; root sibling uniqueness обеспечивается сервисной проверкой, а SQL UNIQUE с nullable parent не является полной защитой корней. Event отражает item create/update/move/take, но create payload имеет только name/quantity, update aliases/tags хранит новое значение без прежнего, tree edits не имеют events. История полезна для человека, но не является replayable event sourcing и не должна так рекламироваться. Путь истории меняется при reparent (R8). При будущем merge/import нужны явные conflict rules по ID и normalized identity; frozen portable-v1 сейчас корректно отказывается от merge.

### 5. Search
Ф: exact name/alias/attribute, separator normalization, tag, substring и FTS5 с unicode61; SQL ограничивает candidate pool до max(limit×4,20), затем Python ранжирует. Плюс: модель/артикул «CH341A», «GTX 1070», «USB/SATA» хорошо поддержаны через alias/attribute и токены. Минусы: нет stemming, edit distance и транслитерации; русское «кабелем»/украинское «кабелем» против «кабель», «shkaf» против «шкаф», опечатка «мултиметр» не гарантируются. FTS OR-prefix может заполнить первые 20 кандидатов однотокенным шумом до overlap-фильтра и скрыть FTS-only релевантный результат (**Э**, нужен adversarial fixture). Для браузера вместо embeddings сначала: нормализованные alias-синонимы, отдельные коды/артикулы, ограниченный словарь RU/UK форм, опциональный trigram/fuzzy fallback при нулевой точной выдаче, подсказка переформулировки. Embeddings оправданы только если на собранных реальных запросах после этих мер устойчиво остаётся существенная доля семантических miss и простые alias/fuzzy правила становятся дороже поддержки.

### 6. Scale
Ф: item catalog пагинирован, search не гидратирует весь Item table, tree counts сгруппированы, suggestions читают релевантные строки; structural tests это защищают. Но [get_item_history](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/services/inventory.py#L322-L334), [list_location](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/tools.py#L312-L322) и conversation context остаются без лимита. Один часто перемещаемый предмет или большой контейнер способен дать огромный HTML/tool response и контекст модели. Ввести page/limit с total и cursor/offset для этих чтений. Tree search делает полный проход сотен узлов; это приемлемо при 250, индекс пока не нужен.

### 7. Data integrity и recovery
Ф: Alembic packaged, startup exact-head gate, doctor проверяет normalization/cycles/FTS, repair ограничен derived index. Backup/restore использует SQLite backup API и проверяет integrity/FK/revision; portable import проверяет многие domain invariants. Р: full backup может быть SQLite-здоровым при нарушенных domain/FTS-инвариантах, потому что validate_database не вызывает doctor; это не делает backup бесполезным, но нужно показывать оба статуса. Restore требует остановки приложения, однако [код не держит межпроцессную блокировку при swap](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/storage.py#L547-L602): при нарушении инструкции риск открыт. Сначала добавить понятную preflight-проверку/предупреждение и rehearsal восстановления; не строить сложный supervisor заранее.

### 8. Transaction semantics
Ф: manual update+move выполняется в одном HTTP commit; AgentRunner откатывает исключения, но user message создаётся отдельным commit до работы и остаётся после failed run. Tool errors — данные, не исключения. R3/R4 описывают главные окна. Дополнительный Р: после первого flush мутации SQLite write transaction может оставаться открытой через следующий сетевой LLM round, блокируя другие записи; проверить конкурентным тестом с задержкой provider, прежде чем менять архитектуру. Для синхронной одиночной установки это не повод вводить async.

### 9. Web UI без LLM
Ф: create/edit Item/Category/Location и ID-навигация работают; Item search переиспользует SearchService, blank catalog пагинирован. Недостаёт фильтра unknown, подсказок с evidence, различения «взято»/«потеряно», удобной коррекции последнего действия, поиска по деревьям и списка descendant items. Поисковые результаты ограничены 100 без total/next; это честно подписано, но затрудняет массовые однотипные вещи. История показывает event type и пути, но не payload изменений; пользователь не увидит, что именно исправили. Все эти задачи решаются серверным HTML и небольшими запросами.

### 10. Agent tools
Ф: 14 небольших tools, стабильные ID, read/write boundary. Но search_tags не даёт отдельного mutation primitive; полезность для модели стоит измерить. get_item/get_location/get_category сходны, но типизированные имена уменьшают ошибки ID; сливать их не нужно без данных. Сильнее влияет default-null в move_item и score-based resolution. Для создания названной сущности prior search проверяет нормализованные переставленные токены, но только prompt требует явного намерения пользователя. Минимальное улучшение: обязательные аргументы, typed resolution outcome, receipts и postcondition checks на write.

### 11. Prompt strategy
[Текущий prompt](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/src/ah_there_it_is/agent/runner.py#L18-L26) краток — это достоинство. Код уже обеспечивает ID-preconditions; фразы «не выдумывай» и «ищи перед созданием» помогают модели, но correctness должен определять dispatcher. Правило «создавать только по просьбе» пока не поддаётся механической проверке без явного user confirmation; не стоит добавлять длинный prompt как замену. После R1–R5 prompt можно сократить до коммуникации, уточнения и различения known/inferred.

### 12. Testing strategy
Ф: 263 теста по review Stage 22, 42 offline scenarios с независимыми persisted-state checks, wheel/migration/recovery и provider contract. Слепые зоны: omitted location_id; singleton слабый FTS candidate; mutation-success затем tool-error/final; crash между commits; история после tree reparent; длинный conversation/history; украинские запросы. Некоторые corpus checks для read-only случаев проверяют только no_mutation, тогда как mock сам ожидает конкретный get_item: это доказывает маршрут backend, но не правдивость финального ответа реальной модели. Добавлять focused adversarial tests, не увеличивать корпус однотипными позитивными кейсами.

### 13. CI и protocol v4
Ф: [v4](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/agent-tasks/common/v4.md) сохраняет seed отдельным обычным commit, запрещает rebase/squash, один implementation PR. [Workflows](https://github.com/buzlet/ah-there-it-is/blob/30c391ac44c0c32d5b4c62c62914740cc1e06ae5/.github/workflows/ci.yml#L6-L12) запускаются на PR с code changes и игнорируют docs-only; реальный Stage 22 выполнен по этой схеме. Р: гарантия «нет параллельной работы» организационная, не машинная; если main уйдёт вперёд между seed и handoff, агент корректно остановится, seed не исчезнет, но stage задержится. Проверка ancestor и exact base нужна; не добавлять сложный orchestrator service. При включении required checks docs-only path filtering надо согласовать с branch protection.

### 14. Security и privacy
Ф: installed serve по умолчанию bind 127.0.0.1, но --host принимает любую строку; HTTP API не имеет authentication. Для сознательного LAN/public bind это доступ к чтению/мутации всего инвентаря. Prompt injection через description/attributes попадает в tool response, после чего модель может вызвать разрешённые tools; backend защищает ID, но не намерение. На localhost риск ниже, всё же malicious imported data способны исказить ответ и действие. Не нужен enterprise auth; достаточно host guard/ясного предупреждения при non-loopback и optional local token при удалённом доступе. Trace retention и extra_body — R10.

### 15. Что строится зря
Без доказательства использования не расширять replay/experiment dashboard, сложные metric aggregates и provider-specific probe сценарии. Не переписывать в microservices, vector DB, async, SPA и не создавать общий CRUD/repository framework. Повторы stage status в трёх верхнеуровневых документах — конкретная цена процесса уже сейчас; свести к указателю на immutable archive.

### 16. Чего не хватает
Самая дорогая реальная работа — занести и затем поддерживать сотни вещей. Empty-db bootstrap хорош для старта, но не помогает добавить вторую коробку из 200 позиций в уже живой инвентарь. Нужны preview, conflict report и ручное подтверждение batch-import; автоматический merge по именам опасен. Другая повседневная задача — быстро понять, какие вещи без известного места и когда их последний раз видели. Не строить фото/QR прежде этих задач.

### 17. Если начать заново
Оставить Python/FastAPI + SQLite/Alembic + service layer + FTS5 + Jinja + provider protocol + deterministic scenarios. Сделать иначе лишь три вещи: (1) явный typed результат mutation и решение commit/rollback для всего agent turn; (2) единое понятие location disposition — known, unknown/in-use, disposed — без смешения inference с authority; (3) обязательные tool-аргументы и разрешение write target отдельно от поискового rank. Не делить систему на новые сервисы или storage layers.

## Дополнительные вопросы, не заданные исходным списком

1. **Сколько усилий стоит первичный ввод?** Empty-db bootstrap не принимает накопление в живой базе; измерить время ввода 100 реальных предметов и ошибки, прежде чем строить новые LLM функции.
2. **Насколько свежа «известная» локация?** В Item нет verified_at; годовалое место выглядит столь же надёжным, как сегодняшнее. Добавить дату проверки только если пользователь реально поддерживает такую дисциплину.
3. **Как разделить часть quantity?** Сейчас move_item передвигает всю запись. Два кабеля из трёх в разных ящиках требуют нового Item или split primitive; определить правило через реальный сценарий.
4. **Что делать после ошибочного подтверждения?** История immutable, но нет user-facing correction/undo receipt. Простое «вернуть предыдущее место» через обычное новое Event может быть ценнее delete.
5. **Что происходит при долгом вызове провайдера после записи?** Сетевая пауза внутри незавершённого SQLite write transaction может заблокировать ручной UI; воспроизвести с двумя соединениями.
6. **Когда пользователь впервые проверит restore?** CLI backup есть, но автоматического напоминания и восстановления на тестовую копию нет; «backup создан» не равно «данные восстановимы».
7. **Как ограничить бесконечный разговор?** Все prior messages передаются модели при каждом run; без summarization/windowing растут стоимость, задержка и контекстный шум. Нужен bounded recent-window с явными retrieval tools, а не скрытая модельная память.
8. **Какие языки реально поддерживаются?** В corpus нет украинских предложений; смешанные названия есть. Сначала собрать RU/UK/EN query set из фактического пользования и измерить retrieval miss без LLM.

## Рекомендуемые 4 stages для оркестратора

1. **Write safety:** R1, R2, R3, R5; новые adversarial offline tests и mutation receipts без provider tuning.
2. **Idempotency crash consistency:** R4, миграция связки request/run и fault injection; затем проверка блокировки SQLite во время сетевого round.
3. **Manual inventory truth:** unknown/in-use/disposed UX, evidence-based suggestions, читаемая история и решение для одинаковых экземпляров.
4. **Measured retrieval and upkeep:** RU/UK/EN adversarial query suite, проверка candidate starvation, bounded history/context, restore rehearsal; только по измеренным результатам выбирать fuzzy fallback или batch import.

Итог аудита — рекомендации, не обязательный roadmap. Изменений в исходном коде этот audit commit не вносит.
