# Configuration boundary audit

Status: repository audit for issue #101. This is a design baseline; it adds no runtime setting, parser, profile schema, or production value change.

## Decision test and classification

A value is configuration when a named owner has a real reason to vary it across installations or users, the change is meaningful without editing code, and the application can validate a bounded set of values. Every setting needs an owner, a default or an explicit-required rule, and a compatibility story. A literal is not configuration merely because it is easy to move.

| Category | Include | Exclude / default owner |
| --- | --- | --- |
| Domain invariant | Rules required for correct, safe inventory state and mutation history. | Never configurable by operator or user. Developer changes require a product decision and regression coverage. |
| Protocol/API constant | Fixed wire spelling, endpoint, response shape, API limit, or negotiated behavior. | Keep beside its adapter; developer updates it when the external protocol changes. Do not expose a knob that lets a caller violate the protocol. |
| Deployment/operator setting | Host, environment, database path, provider endpoint/model, or runtime behavior that legitimately differs by installation. | Operator/admin changes it, with code validation and explicit production values where omission is unsafe. Not a user preference. |
| Secret/credential | Bearer token, API key, password, OAuth token/private key. | Separate secret source and access boundary; never committed, logged, traced, exported as a user preference, or mixed into ordinary non-secret config. Operator manages it. |
| Product default / UX tuning | Stable defaults such as visible page size, presentation density, or global product copy. | A default may be adjustable when there is a concrete need; keep correctness and protocol bounds out of this layer. Developer owns the shipped default; an operator may override only where supported. |
| Future user preference | A value whose choice can differ for one logical user without weakening correctness or deployment policy. | No user-profile schema or multi-user behavior is introduced here. A user can change only an explicitly allowed, validated preference through future app/chat controls or authorized external tooling. |
| Internal implementation constant | Private buffer sizes, ranking weights, retry caps, or transport mechanics without demonstrated operator/product demand. | Keep in code and tests. Revisit only against measured failures or operational evidence, not because a literal exists. |

Classification questions, in order: Does changing this affect valid state, authorization, mutation safety, idempotency, or durability? If yes, it is an invariant. Is the value fixed by an external contract? If yes, it is protocol. If neither, does it vary by host/provider, product-wide choice, or user choice? Give it only that scope. Is it credential material? Put it on the separate secret path. If no supported owner or concrete benefit exists, keep it internal.

## Recommended layers and precedence

Keep environment variables authoritative for application deployment settings. `get_settings()` reads `os.environ`; `.env.example` documents values but is not loaded by the app. On the U24 host, systemd `EnvironmentFile` is already the deployment-file mechanism: keep ordinary settings in `runtime.env`, Telegram credentials in `telegram.env`, and any selected `LLM_API_KEY` in a separate protected credential source rather than the common file. The `chatgpt-codex` provider reads its external login cache and does not use an API key. Do not add an application YAML/TOML file now: one more parser and precedence path adds operator burden without a current use case. The web bind and Telegram poller already have explicit CLI arguments for process-level settings.

Current resolution is: explicit `AH_THERE_IT_IS_DATABASE_URL` over the `AH_THERE_IT_IS_DATA_DIR`/platform default; environment values over code defaults; command-line host/port/poll values over their parser defaults. `get_settings()` caches the resolved settings for the process, so operators restart the service after changing its environment. Production mode requires a deliberate absolute SQLite URL. Keep provider API keys and bot tokens on the secret source, not in the non-secret settings layer. `CODEX_HOME` selects an external credential location; it does not supply credential content.

Future resolution should be:

```text
committed product default
  -> deployment/operator value or policy constraint
  -> per-user override for allowlisted preference fields only
```

Domain invariants are outside this chain. Protocol constants cannot be overridden. A user preference must remain within operator policy (for example an approved model set and a page-size cap). Secrets resolve through their own credential source and never through preference precedence. Missing per-user fields inherit the current product/deployment default.

If user preferences become necessary, add a narrow, typed persisted preference record keyed by the future logical user identity, with nullable overrides and enumerated fields. Do not add it now or create an unstructured settings JSON blob. This keeps absent/new fields backward-compatible and lets a future app/chat preference flow update only permitted behavior without converting inventory entities or correctness policy into configuration.

## Values to expose now and values to keep in code

The deployment values worth setting explicitly now are the existing database URL, environment, provider/model/endpoint and permitted reasoning effort, provider timeout/retry settings, agent round bound where operationally needed, Telegram API transport settings, Telegram token/allowed ID on its separate secret path, web bind/port, and Telegram poll timeout/update batch. The app already exposes most through env or CLI; the production web unit pins its network bind, while the Telegram unit may pin its current `30`/`100` CLI defaults for a fully explicit process contract. Keep systemd restart/stop behavior in the unit file. Add `AH_THERE_IT_IS_DATA_DIR` to `.env.example` or its documentation when maintaining that operator surface; current support exists even though the example does not list it.

Deliberately keep in code: transaction/rollback and idempotency guarantees; state/quantity/lifecycle validity; authorization and explicit non-local acknowledgement; protocol field names, API endpoints and hard API limits; `MAX_PAGE_SIZE` / tool upper bounds and internal retrieval scan limits; ranking weights; SQLite foreign-key/WAL policy absent evidence; parser, response-size, and connection-pool mechanics; prompt safety policy content; and provider capability maps. User-facing page size, progress style and selected model/provider can be future preferences only after an explicit allowlist/product decision. Russian remains the only supported natural language under current scope; do not add a language preference without a new product decision.

## Names, defaults, and migration

Keep the current environment convention `AH_THERE_IT_IS_<SUBSYSTEM>_<SETTING>` with uppercase snake case and unit-bearing suffixes (`_SECONDS`, `_URL`, `_ID`, `_MAX_RETRIES`, `_RETRY_BACKOFF_SECONDS`). Use `_TOKEN` / `_API_KEY` only for secrets and document the secret source separately. Prefer semantic names over provider/model branding except where an external API contract requires it. Future persisted preference names should be scoped, lower-case semantic paths (for example `telegram.page_size`, `telegram.progress_style`, `location.containment_policy`, and possibly `llm.preferred_model`), with typed values and explicit allowed ranges.

Adding an optional env key is backward-compatible when its code default preserves today’s behavior. Renaming a key requires a compatibility alias and deprecation period. Do not silently change defaults in a deployment-only task. A DB URL/data-directory change changes which inventory is active and needs an explicit data move/validation. A future preference table is an additive schema migration; absent rows/fields inherit defaults and existing Items/Locations/Events remain untouched. Secrets need their own rotation/copy procedure and must never be migrated into the preference store.

## Follow-up groups

1. **Deployment surface documentation:** document `AH_THERE_IT_IS_DATA_DIR`, clarify `.env.example` is illustrative rather than auto-loaded, document a separate credential source for `LLM_API_KEY` if an API-key provider is selected, and pin Telegram `--poll-timeout 30 --limit 100` in the production unit when deployment files are next maintained. Preserve current runtime values.
2. **Telegram UX (#100):** implement the specified best-effort live-draft progress and durable-outcome-specific failure behavior with real observed stages and fixed defaults first; test short requests, refresh cadence, long-wait copy rotation, outcome wording, and failure isolation. Keep copy tied to durable outcomes and do not turn it into a free-form user setting. Consider a coarse per-user progress style only after observing the shared default.
3. **Containment policy (#97):** define deterministic evidence/clarification rules and a global `physical_default`; retain a future `permissive` user choice for logical trees. Do not make uncertain model inference a hard rejection fact. Implement behavior in the Russian semantics work, independently of adding profile storage.
4. **Preference/profile gate:** only after a product decision on user identity/profile management, add typed per-user overrides for visible page size, progress style, interaction verbosity, possibly approved model/effort, and containment policy. Enforce operator allowlists/caps and leave secrets, endpoints, user authorization, language support, and domain invariants out.
5. **Configuration maintenance:** keep env parsing and tests aligned; add new deployment settings only when the owner and operational need are known. Do not create a generic feature-flag framework or application config-file parser as a prerequisite.
