# Implementation + verification protocol v6: selected Bash host

This protocol carries forward the v4 single-assignment lifecycle and the v5 just-in-time autonomous batch rules. Historical `v4.md` and `v5-batch.md` remain the record of U24-only work. For an assignment explicitly issued under v6, the selected host, command prelude, canonical checks and bounded CI policy below replace their conflicting environment and invocation clauses. All seed, scope, review, PR, merge, and batch controls in v4/v5 remain mandatory.

## Launcher contract

The user/orchestrator chooses one profile in the launch prompt. The agent may neither infer a profile nor move between profiles, devices, or hosts during an assignment or autonomous batch. Initial profiles are exactly:

```text
execution_profile: u24-bash
device: u24-gpt
repo_path: /home/gpt/projects/ah-there-it-is
```

```text
execution_profile: windows-git-bash
device: <explicit Remote Commander Windows device>
repo_path: /c/path/to/ah-there-it-is
git_bash_exe: C:\Program Files\Git\bin\bash.exe
```

`repo_path` for Windows is an absolute Git Bash path supplied by the launcher. `git_bash_exe` is the explicit native Windows path to Git for Windows Bash. Do not guess paths or choose between Python installations. A future protocol is required to authorize changing host profiles between batch tasks.

## Command execution

All repository, file, terminal, Git, test, verification and GitHub work uses Remote Commander on the selected device. Every independent command batch starts with a fresh deterministic prelude; no previous `cd`, venv activation, export, or interactive shell state may be assumed. Commands and tests are non-interactive.

For `u24-bash`, start each batch in ordinary Bash with:

```bash
cd /home/gpt/projects/ah-there-it-is
export PATH="$PWD/.venv/bin:$PATH"
python -c 'import os,sys; print(sys.executable); assert os.name == "posix"'
```

Confirm the `sys.executable` path is inside the repository's `.venv/bin` (the interpreter file may itself be a symlink). A missing or unusable project venv is a stop condition; never silently use another Python. Worktrees may be used to protect concurrent work, but commands must still begin with this launcher-repository prelude and must explicitly establish the worktree's environment before operating there.

For `windows-git-bash`, Remote Commander may use its native bootstrap only to launch the supplied `git_bash_exe`. Run the complete command batch inside that Bash process, preferably with non-interactive `bash -lc` or equivalent. Do not depend on mintty or an interactive terminal. Within Bash, start every batch with the launcher-provided path and:

```bash
cd "$repo_path"
export PATH="$PWD/.venv/Scripts:$PATH"
export PYTHONUTF8=1
export PYTHONIOENCODING=utf-8
python -c 'import os,sys; print(sys.executable); assert os.name == "nt"'
```

Confirm `sys.executable` has its path inside this repository's `.venv/Scripts` and is native Windows Python. The first Windows pilot may explicitly provision that venv before lifecycle start. If the venv is absent or unusable, stop. Never fall back to MSYS Python, WSL, PowerShell Python, U24, another device, or another shell. PowerShell and cmd are not implementation, Git, test, editing, or lifecycle paths.

### Windows preflight before a seeded branch

Run from Git Bash and record concise results:

- `MSYSTEM` is present and identifies Git for Windows/MSYS; `uname` agrees with that environment.
- `bash --version`, `git --version`, `just --version`, and `python --version` work; Python satisfies `pyproject.toml`.
- The deterministic prelude is active; `python` reports `os.name == "nt"` and has its path in `.venv/Scripts`.
- `repo_path` exists and `git rev-parse --show-toplevel` identifies the expected repository.
- The worktree is clean before lifecycle start.

A failed preflight stops the assignment. Do not change profile to make it pass.

## Assignment and batch lifecycle

For a single assignment, verify the exact seeded branch and clean current `origin/main`, record `seed_sha` and `base_main_sha`, and confirm exactly one ordinary seed commit whose parent is `origin/main`. Continue on that branch; do not make a replacement branch. The issued assignment and seed are immutable: no amend, rebase, squash, reset-away, or force-push history rewrite.

For a pre-issued batch, first verify the immutable control SHA, control branch, manifest and task specs using Git at that SHA. Sync clean `main`; verify manifest prerequisites; record batch-start main. Seed tasks only in listed order, just in time after the predecessor merges. Copy exact spec bytes from control SHA; for the first task also copy the immutable protocol/manifest to their declared destinations; make one ordinary seed commit. Confirm its parent is current `origin/main`. An unexpected external `origin/main` advance after batch start stops the batch. Do not add, reorder or choose tasks, product policy, or roadmap.

For each assignment: implement only issued scope in later commits; self-review `seed_sha..HEAD`; run focused checks and fix local failures; run the complete canonical set on final code; update factual completion docs and a review record; push and open one implementation PR; correct failures on the same branch; require all applicable checks on the current PR head to pass; merge with a merge commit; sync clean `main` and confirm the seed is its ancestor. Preserve v4/v5 review provenance fields, including batch ID, control SHA, and preceding merge or batch-start SHA for batch tasks. Do not weaken runtime or application assertions to accommodate an unobserved host difference.

## Canonical verification

The current full local set is exactly:

```text
just check
just migration-check
just corpus-check
just scenario-check
just scenario-eval
just retrieval-eval
just provider-contract
```

Invoke each recipe in its default Justfile form, without restating default corpus, scenario, or output arguments. Focused checks supplement this set. Temporary databases and reports must use Python/OS temporary-directory facilities, avoid ambiguous MSYS path conversion into native SQLite URLs, and leave the worktree clean. A failed check is diagnosed and corrected, then the full set is rerun on final code. Manual live provider/model probes remain outside normal gates unless assigned.

## Bounded CI and merge

Do not use `gh ... --watch` or another unbounded interactive watcher. Poll or block finitely against the current PR head with an explicit overall limit of 30 minutes per head by default. If checks remain queued/running at the limit, refresh durable status once and report an infrastructure blocker; do not start duplicate runs because a poll timed out. Correct own implementation failures on the same PR and repeat local verification and bounded CI. Merge only after current-head applicable checks succeed, using a merge commit. No permanent Windows CI matrix or duplicate full application job is implied by this host profile.
