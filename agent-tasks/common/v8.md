# Implementation + verification protocol v8

This is the only active implementation protocol.

## Core lifecycle

Every issued implementation unit is an integrated batch. A batch may contain one or many tasks, but it has exactly:

- one immutable control SHA;
- one implementation branch;
- one batch seed commit;
- ordered task checkpoints;
- one cumulative self-review;
- one final pull request;
- one final CI gate;
- one merge commit.


## Execution

### ChatGPT sandbox

```text
host_profile: chatgpt-sandbox
execution_channel: sandbox
execution_user: sandbox
workdir: /mnt/data/<issued-patch-name>
```

Sandbox execution is supported only when the launcher explicitly selects it.

The source of truth is an exact CI artifact named `sandbox-bundle-<start-main-sha>`.
Before edits, verify `.sandbox/MANIFEST.txt` records the launcher-declared upstream
commit SHA. `make sandbox-bootstrap` creates a synthetic local Git baseline
tagged `sandbox-base`; its local commit SHA is not the upstream GitHub SHA.

All edits, local Git commits, Python, Make and tests stay under the issued
`/mnt/data/<issued-patch-name>` workdir.

Run:

```text
make sandbox-bootstrap
```

before Python verification. It creates a local venv, bridges the preinstalled
`/opt/pyvenv` site-packages through a local `.pth` file, installs only this
project from local source with `--no-index --no-build-isolation --no-deps`, and
validates this project's declared requirements. The artifact ships no dependency
wheelhouse. Do not use shell network access, `git fetch`, online `pip install`,
or ad-hoc dependency downloads. If bootstrap reports a mismatch, stop and request
a fresh artifact or explicit dependency decision.

The sandbox Python 3.13 run is valid implementation verification for this channel
but does not replace the authoritative exact-head application CI on Python 3.12.

GitHub/control operations use the GitHub connector rather than shell network
access. If the sandbox agent cannot publish through the connector, it must export
a patch/handoff from `sandbox-base` and report that publication is pending; it
must not claim the remote implementation branch or CI exists.

The sandbox artifact intentionally excludes `agent-tasks/archive/`. Do not try
to reconstruct historical context from the artifact.

Detailed sandbox rules:

`agent-tasks/common/sandbox-execution.md`

### U24 direct shell

```text
host_profile: u24-bash
execution_channel: direct-shell
execution_user: rdu01
workdir: /home/rdu01/projects/<issued-patch-name>
```

The environment is already connected to U24 and repository work is executed directly as OS user `rdu01`.

Do not configure SSH, do not launch a nested Codex process, and do not switch to another OS user.

The launcher must supply one exact, unique patch work directory under:

`/home/rdu01/projects/`

The implementation agent must perform **all** Git, file editing, Python, Make and test operations inside that exact work directory. Do not reuse another checkout and do not operate in `/home/gpt/projects/ah-there-it-is`.

Before mutation verify:

```bash
test "$(id -un)" = "rdu01"
test "$HOME" = "/home/rdu01"
test "$PWD" = "<issued-workdir>"
git rev-parse --show-toplevel
```

If the issued work directory does not yet contain the repository, create the checkout there from the canonical Git remote, then verify the issued start-main/control prerequisites before mutation.

Every independent command batch re-establishes:

```bash
cd "<issued-workdir>"
.venv/bin/python -c 'import os,sys; assert os.name == "posix"; print(sys.executable)'
```

The repository-local venv belongs to this patch checkout. If absent, create/install it in this work directory using the project's normal development install before tests. `make` recipes automatically prefer `.venv/bin`; direct Python commands use `.venv/bin/python`.

A user mismatch or path mismatch is an infrastructure stop condition. Do not repair it with `sudo`, `su`, ownership changes or by using another checkout.

## Default reading set

Read only:

1. `AGENTS.md`;
2. exact issued manifest/task specs from the immutable control SHA;
3. this protocol;
4. relevant source/tests.

Do not recursively read `agent-tasks/archive/`.

## Manifest contract

The immutable manifest defines:

- batch ID;
- expected start-main SHA;
- implementation branch;
- ordered task list;
- exact task spec paths;
- focused checks for every task;
- final integration checks;
- `full_local_required: true|false`;
- stop conditions.

The orchestrator chooses `full_local_required`. The implementation agent must not change it.

## Start

Before mutation:

- verify exact control SHA and task bytes;
- verify `origin/main` equals issued start-main;
- verify clean worktree;
- verify selected execution host/channel;
- verify project venv;
- create the one issued implementation branch from start main.

Create one ordinary batch seed commit containing the active issued batch material required by the manifest.

Do not amend, rebase, squash, reset away or force-rewrite the seed.

## Task checkpoints

Execute tasks only in manifest order.

For each task:

1. implement only that task;
2. self-review the task diff since the previous checkpoint;
3. run only the task's declared focused checks;
4. run `make compile`;
5. run `git diff --check`;
6. run only conditional checks declared for that task;
7. after a failure, rerun the narrow failing test first;
8. once corrected, rerun the task's complete focused set once;
9. commit the task checkpoint;
10. record concise verification/correction facts in the batch review.

Do not run the full repository suite after each task.

Do not add undeclared broad checks merely "to be safe".

If a task cannot reach a green focused checkpoint, stop the batch.

## Conditional checks

Declare only what is relevant:

- migration/storage → migration/storage/restore focused checks;
- search → search/retrieval/scale checks;
- application scenario behavior → affected scenarios or scenario evaluation;
- provider/tool schema → `make provider-contract`;
- packaging/runtime/assets → installed-wheel/runtime focused tests;
- platform/process tooling → dedicated tooling tests.

## Final local verification

After the last task always:

- run the union of final focused/integration checks declared by the manifest;
- self-review the cumulative `seed..HEAD` diff;
- ensure the worktree is clean except intentional review/status files.

If `full_local_required: false`, do not run repository-wide `make check` locally. CI owns the full regression proof.

If `full_local_required: true`, run:

```text
make check
make migration-check
make corpus-check
make scenario-check
make scenario-eval
make retrieval-eval
```

`tools/agent/canonical_verifier.py` may supervise this sequence.

Typical reasons for `true`: host/platform, migrations, storage/restore/WAL, packaging/runtime, verification-framework or CI-boundary changes.

The agent may not promote `false` to `true` itself.

`make provider-contract` is a focused recipe, not part of universal full-local verification, because those tests already run inside full pytest.

## Review

Use one review record for the batch. It is committed before the pull request and therefore contains only facts knowable at that commit:

- batch/control/start-main/seed provenance;
- one section per task with commit range, focused checks and correction count;
- cumulative final self-review;
- final local verification required by the manifest;
- deviations/blockers known before PR creation.

Do not put self-referential or future facts in the committed review. In particular, the review does not attempt to record its own final PR-head SHA, authoritative CI result, merge SHA or final-main SHA.

Do not create repetitive per-task review files.

## Pull request and CI

Open one pull request after all task checkpoints are green.

CI is the authoritative repository-wide merge gate. Require all applicable checks for the exact final PR head.

Application CI retains full pytest, coverage, migration check, corpus/scenario checks, full scenario evaluation and retrieval evaluation. Applicable provider-contract workflow checks must also be green.

Use bounded CI observation; `tools/agent/ci_waiter.py` is preferred when available.

## CI correction

If CI fails:

1. reproduce the narrowest failing check locally;
2. fix;
3. rerun that narrow check;
4. rerun the affected focused/integration set;
5. push;
6. let CI perform the full regression again.

Do not automatically rerun full local regression before every CI retry unless the manifest requires full local verification and the correction invalidates that proof.

## Merge

Merge only the final green PR with a merge commit.

Then sync clean local main, verify seed ancestry and verify local main equals origin/main.

## Completion report

After merge, return the externally reported completion facts that cannot be committed into the pre-PR review without creating a self-reference:

- PR number/URL;
- exact final PR head SHA;
- authoritative applicable CI result for that exact head;
- merge commit SHA;
- final synchronized main SHA;
- seed ancestry proof;
- any post-review deviations or CI correction count.

The completion report is execution evidence; it is not retroactively written into the already-merged batch review.

## Failure semantics

If task N fails before final PR, stop. Do not merge partial batch by default.

Unexpected external `origin/main` advance after batch start is a stop condition unless the manifest explicitly authorizes integrating that exact advance.

## Authority

The implementation agent does not choose new tasks, product semantics, dependencies, execution channel, broader test scope or whether full local verification is required.
