# Implementation + verification protocol v8

This is the only active implementation protocol.

## Core lifecycle

Every issued implementation unit is an integrated batch. A batch may contain one or many tasks, but it has exactly:

- one immutable control SHA;
- one implementation branch;
- one batch seed commit;
- ordered task checkpoints;
- one cumulative self-review;
- one final pull request;
- one final CI gate;
- one merge commit.


## Execution

```text
host_profile: u24-bash

repo_path: /home/gpt/projects/ah-there-it-is

```

The environment is already connected to U24. Do not configure SSH and do not launch a nested Codex process.

```bash
id -un
printf '%s\n' "$HOME"
```

Expected: `gpt` and `/home/gpt`.

Every independent command batch re-establishes:

```bash
cd /home/gpt/projects/ah-there-it-is
export PATH="$PWD/.venv/bin:$PATH"
python -c 'import os,sys; assert os.name == "posix"; print(sys.executable)'
```

## Default reading set

Read only:

1. `AGENTS.md`;
2. exact issued manifest/task specs from the immutable control SHA;
3. this protocol;
4. relevant source/tests.

Do not recursively read `agent-tasks/archive/`.

## Manifest contract

The immutable manifest defines:

- batch ID;
- expected start-main SHA;
- implementation branch;
- ordered task list;
- exact task spec paths;
- focused checks for every task;
- final integration checks;
- `full_local_required: true|false`;
- stop conditions.

The orchestrator chooses `full_local_required`. The implementation agent must not change it.

## Start

Before mutation:

- verify exact control SHA and task bytes;
- verify `origin/main` equals issued start-main;
- verify clean worktree;
- verify selected execution host/channel;
- verify project venv;
- create the one issued implementation branch from start main.

Create one ordinary batch seed commit containing the active issued batch material required by the manifest.

Do not amend, rebase, squash, reset away or force-rewrite the seed.

## Task checkpoints

Execute tasks only in manifest order.

For each task:

1. implement only that task;
2. self-review the task diff since the previous checkpoint;
3. run only the task's declared focused checks;
4. run `just compile`;
5. run `git diff --check`;
6. run only conditional checks declared for that task;
7. after a failure, rerun the narrow failing test first;
8. once corrected, rerun the task's complete focused set once;
9. commit the task checkpoint;
10. record concise verification/correction facts in the batch review.

Do not run the full repository suite after each task.

Do not add undeclared broad checks merely "to be safe".

If a task cannot reach a green focused checkpoint, stop the batch.

## Conditional checks

Declare only what is relevant:

- migration/storage → migration/storage/restore focused checks;
- search → search/retrieval/scale checks;
- application scenario behavior → affected scenarios or scenario evaluation;
- provider/tool schema → `just provider-contract`;
- packaging/runtime/assets → installed-wheel/runtime focused tests;
- platform/process tooling → dedicated tooling tests.

## Final local verification

After the last task always:

- run the union of final focused/integration checks declared by the manifest;
- self-review the cumulative `seed..HEAD` diff;
- ensure the worktree is clean except intentional review/status files.

If `full_local_required: false`, do not run repository-wide `just check` locally. CI owns the full regression proof.

If `full_local_required: true`, run:

```text
just check
just migration-check
just corpus-check
just scenario-check
just scenario-eval
just retrieval-eval
```

`tools/agent/canonical_verifier.py` may supervise this sequence.

Typical reasons for `true`: host/platform, migrations, storage/restore/WAL, packaging/runtime, verification-framework or CI-boundary changes.

The agent may not promote `false` to `true` itself.

`just provider-contract` is a focused recipe, not part of universal full-local verification, because those tests already run inside full pytest.

## Review

Use one review record for the batch, containing:

- batch/control/start-main/seed provenance;
- one section per task with commit range, focused checks and correction count;
- cumulative final self-review;
- final local verification required by the manifest;
- PR/head;
- CI results;
- merge SHA/final main;
- deviations/blockers.

Do not create repetitive per-task review files.

## Pull request and CI

Open one pull request after all task checkpoints are green.

CI is the authoritative repository-wide merge gate. Require all applicable checks for the exact final PR head.

Application CI retains full pytest, coverage, migration check, corpus/scenario checks, full scenario evaluation and retrieval evaluation. Applicable provider-contract workflow checks must also be green.

Use bounded CI observation; `tools/agent/ci_waiter.py` is preferred when available.

## CI correction

If CI fails:

1. reproduce the narrowest failing check locally;
2. fix;
3. rerun that narrow check;
4. rerun the affected focused/integration set;
5. push;
6. let CI perform the full regression again.

Do not automatically rerun full local regression before every CI retry unless the manifest requires full local verification and the correction invalidates that proof.

## Merge

Merge only the final green PR with a merge commit.

Then sync clean local main, verify seed ancestry and verify local main equals origin/main.

## Failure semantics

If task N fails before final PR, stop. Do not merge partial batch by default.

Unexpected external `origin/main` advance after batch start is a stop condition unless the manifest explicitly authorizes integrating that exact advance.

## Authority

The implementation agent does not choose new tasks, product semantics, dependencies, execution channel, broader test scope or whether full local verification is required.
