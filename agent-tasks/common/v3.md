# Implementation + verification agent protocol v3

You own the complete execution of one assignment: implementation, self-review, verification, PR/CI iteration, merge, and compact reporting. The orchestrator retains product/architecture direction and assignment design.

## Execution environment

- Stay in the current ChatGPT chat. Do not switch to or hand off the task to Work mode.
- Perform all repository, terminal, and file work through Remote Commander on U24, device `u24-gpt`.
- Do not deliberate about alternative execution environments, browser/computer automation, or other hosts when `u24-gpt` is available.
- Target `u24-gpt` directly instead of spending tool calls discovering devices when the connector already exposes it.
- If `u24-gpt` is unavailable, report that as a blocker and stop. Do not silently fall back to another machine or Work mode.
- Minimize tool calls. Batch related shell commands when that does not broaden the task.

## Start

1. Work in the repository named by the assignment on U24.
2. Run:
   `git switch main`
   `git pull --ff-only origin main`
3. Do not inspect unrelated branches, unrelated PRs, previous CI runs, release state, or unrelated repository history.
4. Read the referenced assignment and only the project files needed to implement it.
5. Create the focused feature branch named by the assignment.

The orchestrator guarantees exclusive handoff: no repository work occurs between assignment publication and your pull.

## Scope

- Implement exactly the requested behavior with the smallest coherent change.
- Do not perform opportunistic refactors, cleanup, dependency upgrades, workflow upgrades, or unrelated documentation changes.
- Do not change versions merely to silence deprecation or runtime warnings.
- Development dependency/tool versions stay aligned with versions available and exercisable in the active development sandbox unless the assignment explicitly requires otherwise.
- Do not add provider/model/network dependencies unless the assignment explicitly requires them.
- If the requested behavior conflicts with an architecture/product invariant or requires a materially new design decision not resolved by the assignment, stop and report a blocker instead of inventing policy.

## Implementation and self-review

1. Implement the assignment.
2. Review the complete branch diff against the assignment and repository invariants.
3. Remove accidental scope creep and confirm every changed file is justified by the assignment.
4. Run focused tests for the changed behavior first when focused tests exist.
5. Fix implementation or test failures caused by the change and rerun the affected focused checks.

Do not ask the orchestrator to perform routine code review, test execution, or failure diagnosis.

## Required verification

For code/schema/runtime changes, unless the assignment explicitly narrows or expands verification, run the canonical project checks from `Justfile`:

- `just check`
- `just migration-check`
- `just corpus-check`
- `just scenario-check`
- `just scenario-eval`
- `just provider-contract`

Use `/tmp` for generated verification artifacts when the recipe allows it so the branch stays clean.

For documentation/process-only changes, verify the diff is clean and internally consistent; full application checks are not required locally, but normal PR CI still applies.

If a canonical check fails:
- diagnose it;
- fix it when caused by the assignment;
- rerun the affected check;
- before delivery, rerun the complete required verification set once on the final implementation.

Do not hide, ignore, or relabel a failure as success. If a failure is clearly unrelated or infrastructure/transient, retry minimally; if it remains unresolved, report it as a blocker.

## Review record

Before opening the PR, create `agent-tasks/reviews/NNNN-r1.md` for the assignment.

Record concisely:
- assignment/protocol;
- implementation summary;
- changed-file scope;
- self-review findings;
- focused and canonical local verification summaries;
- correction rounds performed before PR;
- deviations or blockers.

If PR/CI feedback requires implementation corrections, update the same review record with the correction count/summary before the final corrective push. Do not paste verbose command logs.

## PR, CI, correction loop, and merge

1. Commit and push the verified branch.
2. Open a PR against `main`.
3. Wait for the normal GitHub checks on the current PR head.
4. Inspect failures on your own PR only.
5. If a failure is caused by your implementation, fix it on the same branch, rerun the relevant local checks, update the review record if needed, push, and wait for CI again.
6. Repeat until the current PR head has all required checks successful.
7. Manual/live provider/model probes that are intentionally skipped are not blockers unless the assignment explicitly requires them.
8. When scope review, local verification, and required CI are all successful, merge the PR into `main`.
9. After merge run:
   `git switch main`
   `git pull --ff-only origin main`
10. Confirm local `main` is clean and matches `origin/main`.

Do not begin the next stage or invent the next assignment. Strategy remains with the orchestrator.

## Final response

Return only a compact summary:
- assignment number;
- PR URL;
- implementation branch and final implementation SHA;
- merge commit SHA / resulting `main` SHA;
- changed files or concise changed-file groups;
- focused verification summary;
- canonical verification summary;
- GitHub CI summary;
- number of correction iterations;
- deviations/blockers, or `none`;
- review-record path.

Do not return raw pytest/Alembic/GitHub logs unless a blocker requires evidence.
