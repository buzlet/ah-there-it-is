# Implementation + independent review protocol v9

This protocol applies to batches issued after v9 is merged. Batches already issued
under v8 finish under v8.

## Principles

Git already provides immutable history. v9 keeps only process state that adds
independent value.

Task definition and execution environment are separate:

- **batch file** = what to do and how to verify the work;
- **executor profile** = where/how the agent runs.

## Issued batch

A new batch is one Markdown file:

`agent-tasks/batches/<batch-id>.md`

It contains:

- objective/scope;
- ordered work;
- focused checks;
- final checks;
- `full_local_required: true|false`;
- non-goals/stop conditions;
- one executor link.

Example:

`Executor: agent-tasks/executors/chatgpt-sandbox.md`

Do not copy task text into `agent-tasks/assignments/`.

## Issuance SHA

The orchestrator commits/merges the finalized batch file to `main`.

That resulting commit is the immutable **issuance SHA**.

The task is permanently recoverable as:

`<issuance-sha>:agent-tasks/batches/<batch-id>.md`

No control branch, control SHA or seed is required.

## Orchestrator issuance

Before handing work to an agent, the orchestrator:

1. finalizes the batch file in `main`;
2. records the issuance SHA;
3. pre-creates one implementation branch exactly from that SHA;
4. ensures the selected executor can start from that SHA.

The agent is given only:

- repository;
- batch file path;
- issuance SHA;
- implementation branch.

The executor is obtained from the batch file itself.

No separate launcher is required unless the human interface needs one.

## Minimal start

The agent reads only:

1. `AGENTS.md`;
2. the issued batch file at the issuance SHA;
3. the executor profile linked by that batch;
4. this protocol;
5. relevant source/tests.

Then the executor profile defines the environment-specific bootstrap.

The agent verifies only the executor-specific binding to the issuance SHA and
begins work.

## Main movement

An advance of `main` after issuance is not an implementation stop condition.

Do not rebase/merge current `main` merely because it advanced. The orchestrator
checks current-main compatibility before merge.

If the implementation discovers an actual semantic conflict with concurrent work,
report it; do not guess the integration policy.

## Implementation checkpoints

For multi-part work, ordinary commits are recovery checkpoints.

Recommended:

`work item → focused checks → inspect diff → commit → next item`

These commits have no special lifecycle metadata.

There is no seed, checkpoint journal, checkpoint-SHA registry or per-task review
file.

Do not automatically run `make compile` or `git diff --check` after every
work item unless the batch explicitly requires it.

## Final local verification

Before opening the PR:

- run the batch-declared final focused/integration checks;
- run `make compile`;
- run `git diff --check`;
- inspect the cumulative `issuance..HEAD` diff;
- verify the issued batch file is unchanged;
- ensure the worktree is clean.

If `full_local_required: false`, exact-head CI owns repository-wide regression.

If `full_local_required: true`, run the exact full-local sequence specified by
the batch. `tools/agent/canonical_verifier.py` is optional supervision, not a
lifecycle requirement.

## Implementation PR

Open one PR from the issued implementation branch.

The PR description is the self-review. Keep it concise:

- implemented/fixed;
- verification;
- deviations;
- `DIRECT FOLLOW-UP`;
- remaining risks.

Do not create a committed self-review file unless the batch explicitly requires a
product artifact.

Wait for authoritative CI on the exact PR head and correct only concrete failures.

The implementer does not merge.

Implementation ends with:

`READY FOR REVIEW`

Required handoff facts:

- PR number;
- exact implementation head SHA;
- exact-head CI result/run;
- Direct follow-ups;
- remaining blocker/risk, if any.

No seed ancestry, merge SHA, synchronized-main report or post-merge report is an
implementer responsibility.

## Independent review

The reviewer uses the existing PR and records the exact implementation head
`I` before review.

The reviewer reconstructs requirements from the issuance SHA/batch, architecture
rules and relevant code/tests before relying on the implementer's PR description.

Review should prefer adversarial regression tests over restating existing tests.

### Clean review

If no correction is needed:

`REVIEW COMPLETE — CLEAN`

The branch remains at `I`.

### Corrections

If findings require changes, the reviewer appends ordinary commits to the **same
implementation branch**.

Rules:

- reproduce the defect first where practical;
- add a regression test first where practical;
- make the narrowest correction;
- append only;
- do not amend/rebase/squash previous implementation commits;
- do not force-push;
- do not open a separate correction PR;
- require authoritative CI on the new exact head `R`.

The review correction range is unambiguous:

`I..R`

Reviewer ends with:

`REVIEW COMPLETE — CORRECTED`

and reports:

- review start head `I`;
- final head `R`;
- findings/corrections;
- exact-head CI;
- remaining risks/Direct follow-ups.

The reviewer does not merge.

## Orchestrator integration

Only the orchestrator performs final integration.

Verify:

1. issuance SHA is an ancestor of final PR head;
2. issued batch file is unchanged in `issuance..final-head`;
3. implementation and reviewer correction ranges are understandable;
4. final PR head has authoritative green CI;
5. PR is compatible with current `main`;
6. current-main overlap/conflicts are consciously resolved.

Then merge.

Post-merge CI, main synchronization, archival and process housekeeping belong to
the orchestrator.

## Helpers

Normal v9 work does not use lifecycle state.

- `tools/agent/canonical_verifier.py` — optional for explicitly required durable full-local verification;
- `tools/agent/ci_waiter.py` — optional exact-head observer where supported;
- `tools/agent/lifecycle_checkpoints.py` and `process_state.py` — legacy v8/historical tooling only.

## Stop conditions

Stop/report when:

- the executor cannot establish the issued SHA/environment;
- required dependencies/environment are unavailable;
- focused work cannot be made green without leaving scope;
- a forbidden new product/dependency decision is required.

Do not stop merely because `main` advanced.

## Authority

The agent does not choose new product semantics, dependencies, executor or merge
policy.

The reviewer may correct demonstrated defects inside issued scope, but does not
expand scope.

The orchestrator owns issuance, implementation-branch creation, current-main
compatibility, merge, post-merge verification and archival.
