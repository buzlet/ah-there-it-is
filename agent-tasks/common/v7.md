# Implementation + verification protocol v7

Protocol v7 carries forward the immutable-seed, assignment, autonomous-batch, verification, PR/CI/merge and stop semantics established by v4/v5/v6, while keeping execution host and execution channel explicit.

Historical protocol generations are archived. They are evidence, not current instructions.

## Launcher contract

The launcher explicitly selects:

```text
host_profile: <profile>
execution_channel: <channel>
```

Supported combinations:

| host profile | execution channel | status |
| --- | --- | --- |
| `u24-bash` | `remote-commander` | established |
| `u24-bash` | `direct-shell` | supported execution model |
| `windows-git-bash` | `remote-commander` | prepared; native Windows pilot still pending |

No other combination is authorized unless a future protocol says so.

The selected combination remains fixed for the assignment/batch. The agent may not infer or switch it.

## Common lifecycle

For every supported channel:

- read exact issued control/assignment bytes;
- verify start prerequisites;
- preserve immutable seed history;
- no amend/rebase/squash/reset-away/force rewrite;
- implement only issued scope;
- self-review complete implementation diff;
- run focused checks;
- run complete canonical verification on final HEAD;
- maintain review record;
- use one implementation PR;
- own bounded CI correction loop;
- merge with merge commit;
- sync clean main and prove seed ancestry;
- stop on unresolved product/architecture decisions or issued stop conditions;
- never gain roadmap authority merely from execution autonomy.

For pre-issued batches, tasks are seeded just in time and only in manifest order. Unexpected external `origin/main` advance after batch start is a stop condition unless the issued control explicitly resolves it.

## Canonical verification

The full local set is:

```text
just check
just migration-check
just corpus-check
just scenario-check
just scenario-eval
just retrieval-eval
just provider-contract
```

Invoke the recipes in their default Justfile form unless an issued assignment explicitly changes arguments.

Focused checks supplement this set.

Final delivery requires the complete canonical set on the final implementation HEAD.

## U24 environment invariant

All U24 repository work must run as OS user:

`gpt`

Required state:

```text
HOME=/home/gpt
repo_path=/home/gpt/projects/ah-there-it-is
```

Before repository operations verify:

```bash
id -un
printf '%s\n' "$HOME"
```

Expected user is `gpt`.

Every independent command batch re-establishes:

```bash
cd /home/gpt/projects/ah-there-it-is
export PATH="$PWD/.venv/bin:$PATH"
python -c 'import os,sys; assert os.name == "posix"; print(sys.executable)'
```

The Python executable must belong to the repository venv.

## Channel: remote-commander on U24

Launcher fields:

```text
host_profile: u24-bash
execution_channel: remote-commander
device: u24-gpt
repo_path: /home/gpt/projects/ah-there-it-is
target_user: gpt
```

All repository/file/terminal/Git/test/GitHub work uses Remote Commander on the selected device.

Commands must execute as `gpt`. If the connector exposes an execution-user setting, use it. Otherwise use the local non-interactive user-switch mechanism available on U24 before repository work.

Do not perform project work under another account and then repair ownership later.

## Channel: direct-shell on U24

Launcher fields:

```text
host_profile: u24-bash
execution_channel: direct-shell
repo_path: /home/gpt/projects/ah-there-it-is
target_user: gpt
```

This execution environment is already transparently connected to U24.

There is:

- no SSH connection for the agent to configure;
- no `ssh` command to launch;
- no nested Codex CLI process to launch or supervise;
- no separate Codex JSONL transport contract.

From the agent's perspective, execute as if U24 were the local computer.

The only execution-boundary requirement is the OS user.

If the connected environment starts under another user:

1. switch locally/non-interactively to user `gpt` using the environment's available user-switch facility;
2. verify `id -un == gpt`;
3. verify `HOME=/home/gpt`;
4. enter the repository and venv prelude;
5. perform the complete repository lifecycle under `gpt`.

If becoming `gpt` requires unavailable credentials or an interactive password prompt, stop with an infrastructure blocker.

Do not invent an SSH layer or start another Codex process to solve the user switch.

## Channel: Windows Git Bash through Remote Commander

Launcher fields:

```text
host_profile: windows-git-bash
execution_channel: remote-commander
device: <explicit Windows device>
repo_path: /c/path/to/ah-there-it-is
git_bash_exe: C:\Program Files\Git\bin\bash.exe
```

All repository/Git/test/lifecycle commands run inside Git Bash.

Native Windows Python must come from the repository `.venv/Scripts`.

Do not fall back to PowerShell/cmd/WSL for implementation work.

Assignment 0029 prepared this path, but it is not first-class validated until a native Windows pilot succeeds.

## Seed integrity

The issued seed is immutable historical evidence.

Do not:

- amend it;
- rewrite the issued assignment;
- rebase it;
- reset it out of history;
- squash it;
- force-push rewritten history.

A merge commit must preserve the seed as an ancestor of main.

## Self-review and verification

Before PR:

- inspect `seed_sha..HEAD`;
- remove scope creep;
- run focused checks;
- correct assignment-caused failures;
- run the complete canonical set once on final code;
- keep worktree clean;
- write/update the review record.

Do not ask the orchestrator to perform routine test diagnosis or code review.

## CI policy

Do not use an unbounded interactive watcher.

CI observation must be finite and tied to the current PR head. A normal default overall observation bound is 30 minutes per PR head.

If checks remain queued/running after the bound, refresh durable state once and report an infrastructure blocker rather than launch duplicate workflows.

Only merge when applicable checks for the current PR head are successful.

Manual provider/model probes are outside normal gates unless explicitly assigned.

## Documentation policy

The active default reading set is intentionally small:

1. `AGENTS.md`;
2. exact issued assignment/manifest;
3. this file;
4. relevant source/tests.

Do not recursively read `agent-tasks/archive/`.

Do not read old protocol generations merely to compare wording.

Historical details are retrieved only when the current assignment specifically needs them.

## Review record

Record the normal assignment/batch provenance:

- assignment;
- branch;
- seed and base-main SHA;
- batch/control SHA when applicable;
- implementation summary;
- changed scope;
- self-review findings;
- focused verification;
- canonical verification;
- correction counts;
- CI result;
- merge/main SHA;
- deviations/blockers.

Execution-channel metadata should be concise and non-secret. Never record credentials, authentication files or private key material.

## Stop conditions

Stop rather than invent policy when:

- issued control/assignment cannot be verified;
- start prerequisite is false;
- selected host/channel cannot be established;
- U24 work cannot be executed as `gpt`;
- required project venv is unavailable;
- unresolved product/architecture semantics appear;
- canonical failure remains unexplained;
- CI remains blocked after normal bounded diagnosis;
- credentials/manual authorization are required;
- an unexpected external-main advance violates the issued batch;
- a dependency task did not merge.

Do not skip a failed task or silently change host/channel.
