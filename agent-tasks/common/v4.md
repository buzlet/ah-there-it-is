# Implementation + verification agent protocol v4

You continue an orchestrator-seeded stage branch and own the complete routine execution of that assignment: implementation, self-review, verification, the single implementation PR/CI correction loop, merge, main synchronization, factual stage-completion documentation, review record, and compact reporting. The orchestrator retains product/architecture direction and chooses the next stage.

The purpose of the seeded-branch model is to preserve the exact pre-implementation assignment in immutable Git history while avoiding a separate orchestrator documentation PR and its redundant CI.

## Pre-handoff contract

Before you receive the task, the orchestrator has:

1. accepted the previous implementation agent's compact verification report without repeating its routine diff review, tests, canonical checks, or CI;
2. synchronized `main`;
3. selected the next product/architecture gap using delta-oriented inspection only;
4. created the assignment-named feature branch from that synchronized `main`;
5. created exactly one ordinary **seed commit** containing the new assignment plus required strategy/status documentation;
6. performed only lightweight document/diff/reference consistency checks on that seed;
7. pushed the branch without opening a PR.

No application CI is expected for that seed push. The orchestrator guarantees that no other repository work occurs between seed publication and your initial pull.

## Execution environment

- Stay in the current ChatGPT chat. Do not switch to or hand off the task to Work mode.
- Perform all repository, terminal, file, test, and GitHub work through Remote Commander on U24, device `u24-gpt`.
- Do not deliberate about alternative execution environments, browser/computer automation, or other hosts when `u24-gpt` is available.
- Target `u24-gpt` directly instead of spending tool calls discovering devices when the connector already exposes it.
- If `u24-gpt` is unavailable, report that as a blocker and stop. Do not silently fall back to another machine or Work mode.
- Minimize tool calls. Batch related shell commands when that does not broaden the task.

## Start on the seeded branch

1. Work in the repository named by the assignment on U24.
2. Fetch remote state:
   `git fetch origin`
3. Switch directly to the already-existing branch named by the assignment:
   `git switch <assignment-branch>`
4. Fast-forward it only:
   `git pull --ff-only origin <assignment-branch>`
5. Confirm the worktree is clean.
6. Record the immutable starting point:
   `seed_sha=$(git rev-parse HEAD)`
   `base_main_sha=$(git rev-parse HEAD^)`
7. Confirm the seed is exactly one ordinary commit on top of current `origin/main`:
   `test "$base_main_sha" = "$(git rev-parse origin/main)"`
8. Read `agent-tasks/common/v4.md`, the referenced assignment, and only the project files needed to implement it.
9. Do **not** create another feature branch.

If the seeded branch is not one ordinary seed commit on current `origin/main`, or if the assignment/branch identity does not match, stop and report the handoff inconsistency instead of rewriting history.

## Seed integrity

The initial `seed_sha` is immutable historical evidence of the exact task as issued.

You must not:

- amend the seed commit;
- edit/rewrite the issued assignment file;
- edit/rewrite `agent-tasks/common/v4.md` as part of the assignment;
- rebase the branch;
- reset the seed out of history;
- squash the seed into implementation commits;
- force-push rewritten branch history.

All implementation, tests, corrections, review records, and factual stage-completion updates are later commits. The final merged history must still contain `seed_sha` as an ancestor.

## Scope

- Implement exactly the requested behavior with the smallest coherent change.
- Do not perform opportunistic refactors, cleanup, dependency upgrades, workflow upgrades, or unrelated documentation changes.
- Do not change versions merely to silence deprecation or runtime warnings.
- Development dependency/tool versions stay aligned with versions available and exercisable in the active development sandbox unless the assignment explicitly requires otherwise.
- Do not add provider/model/network dependencies unless the assignment explicitly requires them.
- If the requested behavior conflicts with an architecture/product invariant or requires a materially new design decision not resolved by the assignment, stop and report a blocker instead of inventing policy.

## Implementation and self-review

1. Implement the assignment in commits after the seed.
2. Review the complete `seed_sha..HEAD` implementation diff against the assignment and repository invariants.
3. Remove accidental scope creep and confirm every changed file is justified.
4. Run focused tests for changed behavior first when focused tests exist.
5. Fix implementation/test failures caused by the change and rerun affected focused checks.
6. Do not ask the orchestrator to perform routine code review, test execution, or failure diagnosis.

## Required verification

For code/schema/runtime changes, unless the assignment explicitly narrows or expands verification, run the canonical project checks from `Justfile`:

- `just check`
- `just migration-check`
- `just corpus-check`
- `just scenario-check`
- `just scenario-eval`
- `just provider-contract`

Use `/tmp` for generated verification artifacts when the recipe allows it so the branch stays clean.

If a canonical check fails:

- diagnose it;
- fix it when caused by the assignment;
- rerun the affected check;
- before delivery, rerun the complete required verification set once on the final implementation.

Do not hide, ignore, or relabel a failure as success. If a failure is clearly unrelated or infrastructure/transient, retry minimally; if it remains unresolved, report it as a blocker.

For an explicitly process/documentation-only assignment, the assignment may require only clean/internal-consistency checks. Do not invent application test runs merely because they exist.

## Factual stage completion

When the assignment is fully implemented and the final local verification is green, update the strategy/status documentation so it truthfully records **this assigned stage** as complete/delivered and summarizes what it actually delivered.

You may not select, name, plan, or create the next stage. Do not create the next assignment. That transition belongs to the orchestrator after your merged report.

## Review record

Before opening the PR, create `agent-tasks/reviews/NNNN-r1.md`.

Record concisely:

- assignment/protocol;
- `seed_sha` and `base_main_sha`;
- implementation summary;
- changed-file scope;
- self-review findings;
- focused and canonical local verification summaries;
- correction rounds performed before PR;
- deviations or blockers.

If PR/CI feedback requires implementation corrections, update the same review record with the correction count/summary before the final corrective push. Do not paste verbose command logs.

## Single PR, CI correction loop, and merge

1. Commit and push the fully verified seeded branch.
2. Open **one** PR against `main` only after implementation/self-review/local verification/review-record work is ready. There is no pre-implementation PR.
3. Wait for GitHub checks on your own current PR head. Prefer one blocking/watch command or equivalent handoff rather than repeated conversational polling.
4. Inspect failures on your own PR only.
5. If a failure is caused by your implementation, fix it on the same branch, rerun relevant local checks, update the review record, push, and wait for CI again.
6. Repeat until the current PR head has all required checks successful.
7. Manual/live provider/model probes intentionally skipped are not blockers unless the assignment explicitly requires them.
8. Merge with a **merge commit**. Do not squash or rebase-merge; the seed and implementation commits must remain ancestors in `main`.
9. After merge run:
   `git switch main`
   `git pull --ff-only origin main`
10. Confirm local `main` is clean and matches `origin/main`.
11. Confirm `git merge-base --is-ancestor "$seed_sha" main` succeeds.

Do not begin the next stage or invent the next assignment.

## GitHub CI model

Normal project workflows are PR-oriented:

- ordinary stage/feature branch pushes do not run full application/provider-contract CI;
- a stage PR containing executable/test/schema/packaging/workflow changes runs the normal full required checks;
- pull requests changing only `AGENTS.md`, `HANDOFF.md`, `README.md`, or `agent-tasks/**` do not start the application/provider workflows;
- manual live provider probes remain explicit `workflow_dispatch` operations and never become application gates.

This keeps routine implementation reliability while avoiding redundant CI on the orchestrator seed and duplicate push+PR runs. The repository currently has no required-status-check branch protection. If required checks are introduced later, docs-only path filtering must be reconciled with that protection before those checks are made mandatory.
